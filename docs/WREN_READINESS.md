# Ren/Wren readiness: what works and what remains

**Snapshot:** 8 November 2026. **Repository:** [DGFcorporations/Ren](https://github.com/DGFcorporations/Ren).

## Bottom line

Ren is **not yet a fully active, ready-to-use phone-and-desktop agent**. The repository's default branch, `pilot/voice-memory-browser`, is the separate G1 offline pilot. The Wren desktop/Android prototype is on `feature/wren-desktop-pilot` at `0996494`; it is not merged or deployed. The fetched remote branch list did not include a `main` branch. This audit and its changes are isolated on `review/ren-capability-audit`.

There is one real deliverable today: a Linux x86-64 PyInstaller desktop folder built on this Ubuntu/glibc 2.39 host. Its CLI help and a loopback-only status endpoint worked. It is a 613 MB folder, not a polished installer, and those checks do not exercise screen capture, clipboard, voice, browser, or mouse control. There is no Android APK: this host has no Gradle installation or Android SDK, and the Android source has a Kotlin method mismatch that must be resolved before it can compile.

## Can Ren eventually read and control screens?

**Yes, within platform-supported boundaries, but not by granting one universal permission.** Android AccessibilityService can inspect semantic UI nodes and act on controls that expose accessibility actions. It is enabled by the user in Android settings, and it cannot promise a complete visual view of every app. Pixel screen capture is separate: Android MediaProjection requires user consent for each capture session, and secure windows can be excluded ([AccessibilityService guide](https://developer.android.com/guide/topics/ui/accessibility/service), [MediaProjection guide](https://developer.android.com/media/grow/media-projection), [`FLAG_SECURE`](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_SECURE)). Android clipboard reads are also restricted in the background on modern versions and can be user-visible ([Android clipboard guidance](https://developer.android.com/develop/ui/views/touch-and-input/copy-paste)). Google Play additionally limits how general-purpose apps may use AccessibilityService; a non-accessibility app needs prominent disclosure and consent, and Play's automation policy does not allow unrestricted autonomous planning/execution ([Play policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)).

On Linux, the current implementation is X11-specific. Semantic screen reading can be added through AT-SPI where applications expose accessible widgets. Wayland needs a different path: XDG ScreenCast sessions select screen/window sources, and XDG RemoteDesktop sessions select keyboard/pointer/touchscreen devices; starting those sessions typically presents a user consent dialog ([ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html), [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), [AT-SPI overview](https://www.freedesktop.org/wiki/Accessibility/AT-SPI2/)). A browser extension or browser-protocol adapter is still needed for reliable page-level actions. Separate Windows/macOS adapters and permissions would be needed for those desktop targets; the current standalone build is Linux-only.

The desktop packaging path was missing declared dependencies. This review added optional `wren` and `desktop` extras to `pyproject.toml`, and generated `requirements-wren.lock` (74 resolved packages, Python 3.12, hashes). A PyInstaller build completed; the resulting folder was approximately 613 MB. The packaged executable at `/workspace/ren-review/dist/wren-desktop/wren-desktop` returned help successfully and, launched with `--host 127.0.0.1 --stt mock --token ''`, served `/api/status` with HTTP 200 before being stopped. This proves the packaged Python server starts; it does not prove native floating-window startup or OS-control integrations. The folder is built on Linux x86-64/glibc 2.39 and is not a Windows, macOS, or Android package. The app still depends on host tools such as `xdotool`, `xprop`, `xclip`, ImageMagick `import`, and audio capture tools; those are not bundled by PyInstaller. The review sandbox had `xdotool`, `xprop`, `xclip`, and `parec`, but not `import`, Gradle, or Android SDK tools; that is not a check of the user's workstation.

On the review branch, `pytest -q tests/wren` reports **56 passed**. These are unit/API tests using mocked providers and stubbed build tools, not real phone or desktop-control tests. `ruff check src tests`, Python `compileall`, and `git diff --check` pass. Repository-wide `ruff format --check src tests` reports 31 files that would be reformatted; unrelated files were not mass-reformatted.

The earlier full-repository run, before installing the new Wren extras, reported 260 passed, 23 skipped, 29 failed, 7 errors, and 143 subtests passed. The seven UI setup errors were due to the missing Playwright Chromium binary; additional failures included Wren's then-missing `faster-whisper`/`pyperclip` dependencies, an initial shell-path issue in the new build-helper stubs, and one monitor CLI timeout. The stub path was corrected and Wren's focused suite passed after the new lock was installed; the full repository suite was not rerun with Chromium installed, so it is not green/fully verified.

The Android project targets SDK 34/minimum SDK 26 and Java 17, using Android Gradle Plugin 8.5.0 and Kotlin 2.0.0. A reproducible build needs JDK 17, Gradle 8.7 (preferably a checked-in wrapper), Android SDK Platform 34/build tools, then a compile fix and device/emulator testing. None of Gradle, `adb`, or `sdkmanager` is available here, so no APK exists. The updated `scripts/build_android.sh` now exits nonzero when Gradle is missing and only installs to a connected phone when invoked with `--install`; regression tests cover these guardrails.

## Safe phone-to-workstation design

Use **one authoritative Wren process on the workstation** and make the phone a remote UI/microphone client. The workstation is the device that can see and operate its own desktop; duplicating the agent runtime on the phone would add synchronization conflicts without solving desktop access. The phone should send user-started audio or text over an authenticated WebSocket, the workstation should transcribe/prepare a draft, and the phone and desktop should display state and require confirmation before paste, click, or other consequential actions.

If the existing tunnel is Tailscale, prefer **Tailscale Serve**, not Funnel: Serve proxies a local service to tailnet devices and follows tailnet access controls; Funnel is intended to expose a service to the broader internet. Keep the backend bound to `127.0.0.1`, allow only the paired phone identity to reach the required service port, and keep public Funnel exposure off ([Serve](https://tailscale.com/docs/features/tailscale-serve), [Funnel](https://tailscale.com/docs/features/tailscale-funnel), [grants](https://tailscale.com/docs/reference/syntax/grants)). If the tunnel is another product, use the same private-TLS-and-allowlist pattern.

**Do not expose the current Wren server through any tunnel yet.** Its default host is `0.0.0.0`; the server and Android client contain a fixed fallback bearer token; the Android manifest permits cleartext HTTP; the WebSocket token can be sent in the URL query; and the phone presets include fixed LAN/Tailscale addresses. Replace these with explicit localhost-by-default startup, one-time pairing, device-specific revocable credentials stored securely, dynamic host discovery, HTTPS/WSS, and a tested approval flow before remote operation.

## Remaining work and owner decisions

1. Confirm the tunnel product and restrict it to the workstation/phone pair. Confirm the workstation Linux distribution and whether the real session is X11 or Wayland; this determines which capture/input backend to build.
2. Harden endpoint defaults and replace embedded token/IP values with a one-time pairing flow and revocable per-device credentials. Do this before testing over the tunnel.
3. Finish Android compilation; add a review/approve step before any paste, implement actual microphone capture/streaming, and add MediaProjection only if user-approved pixel capture is needed. Choose private sideload/internal distribution or Google Play, since the AccessibilityService policy path differs.
4. Add and test X11 mouse/keyboard actions and screen-capture tooling, then a Wayland portal backend if required. Add AT-SPI and a browser extension/protocol adapter for semantic browser actions; retain confirmations for high-impact steps.
5. Test on the real workstation and an Android emulator/device, bundle platform-specific native/system dependencies, download/cache the speech model, and build a proper platform installer. Windows and macOS require separate build/permission validation.

No merge, deployment, device install, or tunnel configuration was performed in this review.
